# Release notes

One file per release, named for the version, written BEFORE the tag and
reviewed with the code it describes. The release workflow reads
`docs/releases/<version>.md` and publishes it as the body of the GitHub
release, followed by the standing install-and-verify section.

Written for a person who has just downloaded the app, not for a
contributor reading a log: what changed for them, what it costs, and what
is still not true. A note that claims more than the build can prove is a
bug in the note.

`0.1.2.md` is kept exactly as it was published, before the notes lived
here — the record is what went out, not what we would write today.
