# Terminal Network

## MVP Specification & Global Roadmap

**Рабочие названия:** Terminal Network, Quiet Spaces
**Ядро системы:** Terminal Mesh Kernel
**Ключевой принцип:** живые социальные пространства, которые принадлежат участникам, а не платформе.

---

## 1. Концепция

Terminal Network — это децентрализованный мессенджер и социальная среда, в которой базовой сущностью является не чат, канал или профиль, а Terminal — живое совместное пространство.

Terminal может быть:

* приватной комнатой;
* рабочим пространством проекта;
* музыкальной лабораторией;
* локальным сообществом;
* временной группой;
* BBS;
* публичным цифровым местом;
* интерфейсом к mesh- или радиосети;
* интерактивной сценой;
* пространством для совместного создания цифрового объекта.

Внутри Terminal существуют сообщения, файлы, задачи, голосования, музыкальные фрагменты, состояния участников, AI-агенты, визуальные сцены и другие блоки.

Основная продуктовая идея:

> Общение должно не только создавать поток сообщений, но и изменять общее цифровое пространство.

Сообщение может стать задачей.
Идея — карточкой проекта.
Спор — голосованием.
Аудиозапись — частью композиции.
Серия решений — новой версией общего объекта.

---

## 2. Продуктовая позиция

Terminal Network не является ещё одним централизованным мессенджером.

Это:

> Универсальный социальный интерфейс, способный работать поверх любой сети — от быстрого интернета до локального LoRa-радио.

И одновременно:

> Протокол и клиент, которые не требуют передачи своей социальной жизни владельцу платформы.

Оператор Terminal Network:

* не хранит сообщения;
* не хранит аккаунты;
* не хранит список контактов;
* не хранит социальный граф;
* не управляет единой базой пользователей;
* не является обязательным посредником доставки;
* не может прочитать пользовательские Terminal-пространства.

Система распространяется как программное обеспечение и открытый протокол.

## 3. Ключевые свойства

### 3.1. Local-first

Каждое устройство является полноценным узлом.

Оно самостоятельно хранит:

* криптографическую идентичность пользователя;
* локальные Terminal-пространства;
* подписанные события;
* текущее состояние интерфейса;
* очередь исходящих пакетов;
* настройки хранения;
* список доверенных устройств.

Клиент продолжает работать без интернета.

Пользователь может:

* читать ранее полученные данные;
* писать сообщения;
* создавать объекты;
* изменять сцену;
* добавлять задачи;
* готовить события к отправке.

После появления связи изменения синхронизируются автоматически.

**Почему это важно**

Большинство современных приложений фактически перестают существовать без доступа к серверу. Terminal остаётся рабочим инструментом даже при плохой связи, блокировках, отключениях или работе в автономной локальной сети.

### 3.2. Zero-custody

Terminal Network не хранит пользовательскую информацию на своей стороне.

Данные находятся только:

* на устройствах участников;
* на устройствах, которым пользователь явно доверил архив;
* на временных blind relay-узлах;
* на добровольных community nodes;
* в пользовательских зашифрованных резервных копиях.

**Почему это важно**

Приватность обеспечивается не политикой компании, а архитектурным отсутствием центрального хранилища.

Компания не обещает «не смотреть данные».
У неё просто нет этих данных.

### 3.3. Transport-agnostic

Terminal не зависит от конкретного способа доставки.

Один и тот же Terminal может синхронизироваться через:

* прямое интернет-соединение;
* локальную сеть;
* Wi-Fi Direct;
* Bluetooth;
* пользовательский relay;
* Reticulum;
* Meshtastic;
* LoRa;
* BBS;
* экспортируемый bundle-файл;
* QR-код;
* физический перенос данных;
* будущие транспортные протоколы.

UI, модель событий и социальная логика не зависят от транспорта.

**Почему это важно**

Большинство приложений построены вокруг одного сетевого предположения: есть стабильный интернет и доступный сервер.

Terminal отделяет социальное пространство от физической сети. Один и тот же интерфейс может существовать в городе, локальной мастерской, фестивальном лагере, экспедиции или автономной радиосети.

### 3.4. Graceful degradation

Terminal адаптируется к возможностям соединения.

При быстром интернете пользователь получает:

* изображения;
* файлы;
* аудио;
* анимацию;
* сложные интерактивные блоки;
* синхронизацию в реальном времени.

При низкой пропускной способности остаются:

* короткий текст;
* статусы;
* координаты;
* команды;
* реакции;
* небольшие изменения состояния;
* ссылки-хэши на тяжёлые объекты;
* отложенная очередь доставки.

**Почему это важно**

Радиосеть не должна получать отдельный примитивный интерфейс. Она должна становиться низкополосной проекцией того же самого Terminal.

### 3.5. Shared state, а не только сообщения

Terminal хранит журнал событий, из которого детерминированно собирается текущее состояние пространства.

Примеры событий:

* сообщение отправлено;
* объект создан;
* задача назначена;
* участник изменил статус;
* проведено голосование;
* файл опубликован;
* элемент перемещён;
* создана новая версия;
* участник добавлен или исключён;
* изменена политика Terminal.

Это позволяет использовать Terminal как:

* чат;
* доску;
* проектное пространство;
* сцену;
* журнал;
* коллективный инструмент;
* цифровой мир.

## 4. Основные сущности

### 4.1. Identity

Идентичность создаётся локально и представляет собой криптографическую пару ключей.

Она не требует:

* номера телефона;
* электронной почты;
* имени пользователя на центральном сервере;
* регистрации у оператора.

Identity может иметь локальный профиль:

```yaml
display_name: Pine
avatar: local-content-hash
bio: Creative technologist
```

Профиль передаётся только выбранным пользователям или публикуется добровольно.

### 4.2. Device

У одного пользователя может быть несколько устройств.

Каждое устройство получает отдельный ключ, подписанный основной идентичностью.

Это позволяет:

* отзывать потерянное устройство;
* добавлять новый компьютер;
* различать источник событий;
* синхронизировать личные Terminal между собственными устройствами.

### 4.3. Terminal

Terminal — криптографически адресуемое пространство с собственной политикой доступа.

Минимальная модель:

```yaml
terminal_id: hash
title: Forest Lab
mode: private
retention: participant_defined
membership: capability_based
```

Режимы:

* private;
* invite-only;
* local-discoverable;
* public;
* ephemeral;
* personal;
* broadcast.

### 4.4. Signal

Signal — универсальное событие системы.

```yaml
signal:
  id: content_hash
  terminal_id: terminal_hash
  author: public_key
  device: device_key
  sequence: 42
  timestamp: logical_time
  type: message
  payload: encrypted_data
  previous: previous_hash
  signature: signature
```

Signal может представлять:

* сообщение;
* реакцию;
* изменение объекта;
* голосование;
* координату;
* сенсорное значение;
* команду;
* присутствие;
* файл;
* системное событие;
* изменение состава группы.

### 4.5. Block

Block — интерактивная проекция данных Terminal.

Примеры:

* Chat;
* Notes;
* Tasks;
* Poll;
* Files;
* Map;
* Audio Player;
* Shared Canvas;
* Activity Feed;
* Members;
* AI Agent;
* Sensor Panel;
* Radio Status;
* Generative Scene.

В MVP реализуется ограниченный набор блоков, но модель должна сразу поддерживать расширение через registry.

### 4.6. Transport Adapter

Каждый транспорт реализует единый интерфейс:

```text
start()
stop()
send(envelope)
receive()
discover()
capabilities()
peerState()
deliveryStatus()
```

Transport Adapter сообщает ограничения:

```yaml
bandwidth: low
latency: delayed
max_payload: 240
supports_realtime: false
supports_broadcast: true
supports_ack: partial
supports_files: false
```

Terminal Mesh Kernel решает, какие события можно отправить напрямую, какие следует сжать, отложить или заменить ссылкой на внешний объект.

```text
                   │
┌──────────────────▼───────────────────┐
│         Terminal Mesh Kernel         │
│ Identity · Event Log · Sync · Crypto │
└──────────────────┬───────────────────┘
                   │
┌──────────────────▼───────────────────┐
│       Universal Transport Layer      │
│ LAN · P2P · Relay · File · Radio     │
└──────────────────────────────────────┘
```

### 5.1. Event log

Каждый автор создаёт последовательность подписанных событий.

События образуют проверяемый журнал:

```text
event 41 → event 42 → event 43
```

Узел не может незаметно изменить старое событие, поскольку изменятся хэши последующих элементов.

### 5.2. Materialized state

Текущее состояние Terminal собирается из журнала:

```text
event log
    ↓
deterministic reducers
    ↓
current Terminal state
```

Для изменяемых общих объектов используются CRDT или другие детерминированные структуры слияния.

### 5.3. Synchronization

При соединении узлы не пересылают всю базу.

Они обмениваются кратким описанием состояния:

```yaml
alice: 1..184
bob: 1..96
carol: 1..42
```

После этого передаются только отсутствующие события.

Синхронизация должна быть:

* идемпотентной;
* возобновляемой;
* устойчивой к дубликатам;
* устойчивой к изменению порядка доставки;
* пригодной для редких соединений;
* пригодной для малых пакетов.

### 5.4. Blind relay

В случае отсутствия прямой связи зашифрованный пакет может временно храниться на стороннем узле.

Relay знает только минимум, необходимый для доставки:

```yaml
destination_hint: rotating_hash
expires_at: timestamp
size: 800
ciphertext: bytes
```

Relay не должен знать:

* содержание сообщения;
* название Terminal;
* список участников;
* реальные идентичности сторон.

Любой пользователь может запустить свой relay. Ни один конкретный relay не является обязательным.

## 6. MVP

### 6.1. Цель MVP

Доказать, что полноценное социальное пространство может:

1. существовать без центральной базы;
2. работать offline;
3. синхронизироваться напрямую между устройствами;
4. сохранять проверяемую историю событий;
5. адаптироваться к разным транспортам;
6. превращать сообщения в структурированные объекты;
7. не требовать регистрации у оператора.

MVP не должен пытаться конкурировать с Telegram по количеству функций.
Он должен убедительно показать новую архитектурную категорию.

### 6.2. Главный демонстрационный сценарий

Два пользователя устанавливают приложение.

**Шаг 1. Создание identity**

Каждый клиент локально генерирует идентичность.
Нет регистрации, телефона или электронной почты.

**Шаг 2. Создание Terminal**

Первый пользователь создаёт приватный Terminal:

> Forest Session

Приложение генерирует QR-приглашение.

**Шаг 3. Подключение второго участника**

Второй пользователь сканирует QR и получает capability доступа.

**Шаг 4. Offline-работа**

Пользователи отключаются от интернета.

Каждый может:

* писать сообщения;
* создавать заметки;
* превращать сообщение в задачу;
* менять статус присутствия;
* прикреплять небольшие файлы.

**Шаг 5. Прямая синхронизация**

Устройства оказываются в одной локальной сети и автоматически обнаруживают друг друга.
Все события синхронизируются без сервера.

**Шаг 6. Конфликт**

Оба пользователя offline редактируют один общий объект.
После соединения изменения корректно сливаются.

**Шаг 7. Store-and-forward**

Третий узел получает зашифрованный пакет для отсутствующего пользователя и позже передаёт его адресату.
Третий узел не может прочитать содержимое.

**Шаг 8. Альтернативный транспорт**

Одно короткое сообщение передаётся через экспериментальный Reticulum adapter или эмулятор низкополосного транспорта.
UI остаётся тем же, но автоматически переключается на компактное представление.

### 6.3. Функции MVP

**Identity**

* локальная генерация ключей;
* локальный профиль;
* fingerprint;
* QR-код идентичности;
* encrypted backup;
* импорт backup;
* добавление второго устройства;
* отзыв устройства.

**Terminal**

* создание приватного Terminal;
* присоединение по capability invite;
* список участников;
* роли owner, member, guest;
* удаление участника;
* локальное переименование;
* политика хранения;
* экспорт Terminal bundle.

**Chat Block**

* текстовые сообщения;
* ответы;
* реакции;
* редактирование через новое подписанное событие;
* tombstone-событие удаления;
* локальный поиск;
* статус доставки.

**Object Block**

Минимальный тип структурированного объекта:

```yaml
type: card
title: Record field ambience
status: open
assignee: identity
```

Действия:

* превратить сообщение в карточку;
* изменить статус;
* назначить участника;
* добавить комментарий;
* показать историю изменений.

**Presence**

Не бинарное online/offline, а осмысленные режимы:

* рядом;
* слушаю;
* открыт к разговору;
* занят;
* работаю;
* не беспокоить;
* offline.

Presence является добровольным и имеет TTL.

**Transport**

В MVP:

* localhost transport для тестов;
* LAN peer discovery;
* прямой сетевой transport;
* bundle-file transport;
* blind relay prototype;
* low-bandwidth transport emulator;
* экспериментальный Reticulum adapter как stretch goal.

**Storage**

* локальная зашифрованная база;
* append-only event log;
* materialized state;
* хранение content-addressed attachments;
* пользовательские retention settings;
* очистка временных пакетов по TTL.

**Security**

* подпись каждого события;
* шифрование приватного Terminal;
* верификация последовательности событий;
* защита от повторного воспроизведения;
* ограничение размера пакетов;
* rate limits на неизвестных peers;
* ручная проверка fingerprint;
* предупреждение о неподтверждённой identity.

## 7. Что не входит в MVP

Чтобы не утонуть в масштабе, первая версия не включает:

* голосовые и видеозвонки;
* большие публичные сообщества;
* глобальную рекомендательную ленту;
* полноценную систему плагинов;
* маркетплейс блоков;
* сложную социальную репутацию;
* встроенные платежи;
* криптовалюту или токены;
* постоянное облачное хранение;
* редактирование больших документов;
* масштабные публичные индексы;
* полную поддержку всех радио-протоколов;
* анонимную глобальную сеть;
* обещание абсолютной неотслеживаемости;
* обязательную AI-функциональность.

AI должен появляться позднее как добровольный локальный или выбранный пользователем Block, а не как обязательный посредник всех разговоров.

## 8. UX MVP

### 8.1. Главный экран

Главный экран показывает не глобальную ленту, а список собственных Terminal:

```text
Forest Session
3 новых события · LAN available

Artifact Forge Lab
Последняя синхронизация 2 часа назад

Private Notes
Только на этом устройстве
```

### 8.2. Экран Terminal

Базовая компоновка:

```text
┌─────────────────────────────┐
│ Forest Session              │
│ LAN · 3 peers · encrypted   │
├─────────────────────────────┤
│ Chat │ Objects │ Activity   │
├─────────────────────────────┤
│                             │
│      Current block          │
│                             │
├─────────────────────────────┤
│ Message / Command input     │
└─────────────────────────────┘
```

Пользователь всегда должен видеть:

* через какой транспорт он подключён;
* какие возможности доступны;
* доставлено ли событие;
* сохранено ли оно только локально;
* есть ли ожидающие синхронизации;
* кто способен прочитать данные.

### 8.3. Команды преобразования

Из контекстного меню сообщения:

* превратить в задачу;
* сохранить как решение;
* закрепить;
* создать голосование;
* связать с объектом;
* экспортировать;
* отправить через другой транспорт.

Именно это отличает Terminal от обычного чата.

## 9. Критерии готовности MVP

MVP считается готовым, если выполняются следующие условия.

**Функциональность**

* два новых клиента могут начать работу без регистрации;
* Terminal создаётся без обращения к центральному API;
* приглашение передаётся QR-кодом или файлом;
* сообщения отправляются напрямую в LAN;
* offline-события синхронизируются после восстановления связи;
* конфликты общего объекта сливаются детерминированно;
* третий узел способен временно перенести непрозрачный зашифрованный пакет;
* transport можно заменить без изменения Terminal UI;
* данные переживают перезапуск клиента;
* пользователь может экспортировать и восстановить identity.

**Приватность**

* сетевой оператор не хранит пользовательскую базу;
* relay не способен расшифровать содержимое;
* приватный Terminal нельзя обнаружить без приглашения;
* контакты не выгружаются в глобальный каталог;
* журнал событий проверяется криптографически;
* UI честно показывает ограничения удаления.

**Надёжность**

* повторная доставка не создаёт дубликатов;
* события можно получать в произвольном порядке;
* частично переданная синхронизация возобновляется;
* повреждённые события отклоняются;
* неизвестный peer не может бесконечно заполнять локальное хранилище;
* большие вложения не блокируют передачу коротких сообщений.

**Демонстрация**

Должна существовать воспроизводимая демонстрация:

> Два ноутбука без интернета создают Terminal, работают отдельно, встречаются в LAN, синхронизируют чат и общую карточку, а затем передают сообщение третьему участнику через blind courier или альтернативный transport.

## 11. Global Roadmap

**Цель**

**Главный proof**

Два CLI-узла создают подписанные события и синхронизируются через файл и локальное соединение.

**Почему это круто**

Проект начинает существовать как открытый протокол, а не как UI-концепт, намертво привязанный к одному приложению.

* LAN discovery;

* encrypted local storage;

**Главный proof**

Люди могут пользоваться Terminal без аккаунта и без доступа к интернету.

**Почему это круто**

**Почему это круто**

## 13. Основные риски

**Сложность P2P**

NAT, мобильные платформы и фоновые ограничения усложняют прямые соединения.

Решение: необязательные заменяемые relay, LAN-first, bundle transport и честное описание сетевых ограничений.

**Потеря ключей**

При отсутствии центрального аккаунта восстановление невозможно без backup.

Решение: понятный onboarding, recovery package, trusted devices и социальное восстановление в последующих версиях.

**Спам и злоупотребления**

Отсутствие центрального сервера не означает отсутствие атак.

Решение: capability-based access, локальные trust policies, quotas, proof-of-work или другие cost-механизмы для неизвестных отправителей.

**Сложность группового шифрования**

Удаление участников и смена ключей требуют аккуратной модели epochs.

Решение: в MVP ограничить размер групп и заложить заменяемый cryptographic membership layer.

**Ложные обещания приватности**

P2P-сеть не гарантирует абсолютной анонимности, а получатель может сохранить уже расшифрованное сообщение.

Решение: честная threat model и отсутствие маркетинговых обещаний, которые невозможно выполнить технически.

**Слишком широкий scope**

Проект легко превратить одновременно в Telegram, Discord, Notion, Nostr, Meshtastic и метавселенную.

Решение: MVP доказывает только identity, Terminal, события, offline-sync, transport abstraction и message-to-object transformation.

## 15. Итоговая формула проекта

Terminal Network объединяет:

```text
local-first software
+ cryptographic identity
+ signed event logs
+ deterministic shared state
+ capability-based access
+ end-to-end encryption
+ transport-independent synchronization
+ optional blind couriers
+ interactive social blocks
+ graceful low-bandwidth degradation
```

Результат — не просто мессенджер без серверов.

Это универсальная среда, в которой люди могут создавать собственные социальные пространства, переносить их между сетями, продолжать работу offline и самостоятельно выбирать, где физически находятся их данные.

Главный критерий успеха проекта:

> Terminal должен оставаться настоящим, полезным и живым пространством даже тогда, когда исчезают облако, стабильный интернет и компания, которая написала первый клиент.
